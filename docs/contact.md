# LBS contact delivery

The browser posts JSON to `/api/web-leads`. `api/web-leads.js` validates it and awaits
one plain-text Resend notification. No database, queue, acknowledgement, subscription,
or external application backend is involved. The production rate limit is a separate
Vercel firewall rule; the handler does not pretend to enforce a distributed limit in memory.

## Configuration (not configured by this change)

Production-scoped, server-only Vercel environment variables:

| Name | Purpose |
| --- | --- |
| `RESEND_API_KEY` | Resend sending-only key restricted to the verified LBS domain |
| `CONTACT_FROM_EMAIL` | `website@landbasedstrategies.com` |
| `CONTACT_TO_EMAIL` | `alex@landbasedstrategies.com` |

`VERCEL_ENV` is supplied by Vercel. Delivery is disabled unless it is `production`.
Do not set it manually to enable local or Preview sends. Never put real credentials in
tests, browser code, Git, or shell commands. Preview/local tests inject a mock transport.

After separate authorization, in Resend's free transactional account:

1. Add `landbasedstrategies.com` as a sending domain. This exact domain is necessary
   for the approved `website@landbasedstrategies.com` From address.
2. Inspect existing DNS before adding records. Add only the DKIM, SPF, and return-path MX
   records generated by Resend for this domain and chosen region. Their exact values
   must come from Resend, not this document. Preserve existing apex MX, SPF, DMARC,
   website records, nameservers, and canonical-host settings. Stop on a record conflict.
3. Verify the domain in Resend; wait until sending verification passes. Do not enable
   inbound receiving, open tracking, or click tracking for this contact integration.
4. Create a sending-only API key restricted to this domain. Configure the three
   variables above for Production only, without displaying the key.
5. Deploy only after authorization. Environment changes take effect in a new deployment.

See https://resend.com/docs/dashboard/domains/introduction and
https://resend.com/docs/api-reference/emails/send-email.

## Vercel firewall (requires separate setup authorization)

In the existing LBS project, Firewall > Configure > add a custom rule:

- Name: `LBS contact submissions`.
- Conditions: request method equals `POST`, AND request path is either
  `/api/web-leads` or `/api/web-leads/`. Do not scope by Origin header.
- Action: Rate Limit; key/group by client IP only (not IP plus path).
- Limit: 5 requests; window: 600 seconds; fixed window; exceed action: Rate Limit (`rate_limit`, HTTP 429), not Deny (403).
- Apply only this rule; preserve all other firewall and project settings.

This counts attempts, not just delivered inquiries. A fixed-window boundary can allow
two bursts close together. Shared-IP users share the allowance. Native firewall rejection
is handled by the existing generic error UI; it need not return the handler's JSON.
If the project's UI does not offer these settings, stop rather than substitute a wider rule.
Verify both slash variants share the limit after setup. See
https://vercel.com/docs/vercel-firewall/vercel-waf/rate-limiting.

## Tests and behavior

Run `npm test` using Node 22. Tests inject mock Resend responses and require no credentials
or network access. Tests cover validation, all five public labels, compatibility, privacy,
provider failures/timeouts, and retry keys. Browser QA must also use a mock transport.
Do not run live email calls as part of routine tests.

Limits: 32 KiB raw body; name 200, email 254, company 300, wire message 5,200 characters.
The form caps user message input at 5,000; remaining room accommodates the existing topic
prefix. The three legacy topic values and unused legacy fields remain compatible. Old
clients without homepage/submission_id are accepted; new clients supply both. Unknown
fields cannot change sender, recipient, subject, or provider configuration.

POST and JSON only. Cross-origin browser requests are rejected. Missing Origin is accepted
for non-browser clients; Origin checks and the honeypot are not authentication. Production
only accepts the canonical browser origin. A filled honeypot returns generic success but
sends no email. No inquiry PII is written to application logs.

Provider calls time out after 10 seconds; the browser aborts after 20 seconds. Failure keeps
the entered data. Success resets the form. Unchanged retries in the same page session use
the same Resend idempotency key and email body; keys expire at Resend after 24 hours.
Reloading the page loses the retry key. There is no durable recovery queue.

## Tracing and production acceptance

Use the JSON response or `X-Request-Id` to locate Vercel runtime events: `received`, then
a validation/configuration/provider outcome. Only IDs, event categories, status, and elapsed
time are logged. Provider acceptance includes its message ID. Do not enable body/request
payload logging. Raw exceptions and provider error bodies are deliberately omitted.

`provider_accepted` establishes handoff, not inbox delivery. Check the matching Resend
delivery record and recipient mailbox to establish delivery. Provider records contain the
email itself; limit account access and observe its retention policy. Runtime log retention
is governed by the existing Vercel plan; no permanent audit history is promised.

After separately authorized deployment, verify endpoint routing, safe rejection paths,
and the firewall without triggering delivery. Then make one explicitly authorized synthetic
submission and correlate browser status, runtime request ID, Resend ID/delivery status,
and actual receipt at the approved mailbox. Confirm Reply-To and no acknowledgement.
Review normal site routing and Git status. Leave the dormant Fly application untouched.
